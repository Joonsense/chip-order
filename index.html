Your model is the contract.

A chip that matches a vague spec is a guess. A chip that matches your Python model on every clock is not. Write the model here, run it on random inputs, and look at the waveform before you order. This runs the same loop as the cocotb test that ships in your repo, in your browser, nothing uploaded.

Python loads on the first run (about 7 MB, once).
The waveform shows up here: inputs you drove, outputs your model says the chip must produce.
cycle 096 shown

The contract: Model.reset(), and Model.cycle(ui_in, uio_in) returns (uo_out, uio_out, uio_oe) as seen just before the next rising edge, then advances one clock. Optional stimulus(rng, cycles) yields (ui_in, uio_in[, rst_n]) so the test drives your protocol, not noise.

Nothing ships on the agent's word.

The agent only writes Verilog. Your model and the test are fixed, and it cannot touch them. Every failure goes back to the agent with the first mismatching clock, the inputs, what your model expected and what the chip did.

01

You write the spec and model

Plain English for the pins and protocol, Python for the exact behaviour, including latency. Ambiguity gets settled here, not in silicon.

Catches a model that breaks its own contract before any Verilog exists.

02

The agent writes RTL

Verilog-2005 for one tt_um_* module with the Tiny Tapeout pins. Lint errors, mismatches and size problems go back to it, up to a fixed number of attempts.

Catches lint errors, latches, wrong widths via Verilator -Wall.

03

Cycle exact simulation

The cocotb test that ships in your repo drives your stimulus every clock and compares every output pin with your model, over three seeds with a reset in the middle.

Catches off by one clock, wrong reset, X on outputs.

04

Same test on the gates

Yosys synthesizes the RTL and the netlist runs the same test. Then sky130 area and 50 MHz timing are predicted with a model fitted to 11 real layouts.

Catches simulation and synthesis disagreeing, designs too big for the tile.

05

The test is tested

Copies of the RTL with one operator flipped run through the test. Each one should fail. Survivors are listed in your report: either harmless or a gap in your stimulus.

Catches a test that passes anything.

06

Official layout flow

Your repo runs the Tiny Tapeout gds, precheck and gate level workflows in GitHub Actions: placement, routing, DRC, LVS, antenna, timing at slow corner.

Catches anything that would get a shuttle submission rejected.

What makes a good order

  1. Fits Tiny Tapeout I/O: 8 inputs, 8 outputs, 8 bidirectional pins, one clock.
  2. Digital and synchronous. No analog, no RAM macros, no second clock domain.
  3. Fits a few tiles: think counters, controllers, protocol engines, small DSP and ML datapaths.
  4. A model that runs in the box above without errors, with a stimulus that exercises your protocol.

Not sure it fits? Open the order anyway. A failed order costs you nothing and the report says exactly where it stopped.

Questions

Is this a real chip?

It is a design that passes the same layout and checks Tiny Tapeout requires for a shuttle. It becomes silicon when you submit the repository and buy a tile at app.tinytapeout.com. None of the example designs has been fabricated yet, and we say so in every report.

Why a Python model instead of just a spec?

Because English leaves the timing open. "Outputs the count" does not say which clock. A cycle-level model does, and it turns into a test the agent cannot argue with.

What if the agent can't do it?

You get the report anyway: each attempt, the stage it failed at, and the first mismatching clock. Often that points at the model, not the RTL.

Which agent?

Claude, run as a tool-less code generator. It only produces Verilog text. Simulation, synthesis, mutation testing and layout are done by Icarus, Verilator, Yosys, OpenSTA and the Tiny Tapeout LibreLane flow.

Can I bring my own Verilog?

Yes. Attach it to the order and it goes through the same checks without the agent. That alone is a useful second opinion before a shuttle deadline.
